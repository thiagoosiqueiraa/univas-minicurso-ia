Crie um arquivo chamado de code-standards.md, coloque na pasta .agents/rules e vincule no AGENTS.md, nesse arquivo vamos ter padrões de codificação, quero que você escreva em português e dê exemplos para cada uma das situações a seguir: não insira comentários (somente caso seja absolutamente necessário, por exemplo, para explicar uma expressão regular complexa), nunca crie classes ou arquivos (.ts) com mais de 100 linhas, os métodos e funções devem ter no máximo 30 linhas (caso o comportamento implementado seja maior, divida em mais métodos), não aninhe mais de 3 if/else e dê preferência pelo uso de cláusulas guarda, tipo early return, para evitar o acúmulo de lógica condicional), evite utilizar mais de 3 parâmetros em métodos e funções (caso seja necessário, crie objetos parâmetro), evite linhas em branco DENTRO de métodos e funções (entre membros de classes ou entre funções em um arquivo, tudo bem), extraia números/strings mágicos para constantes (tornando os conceitos mais claros), declare variáveis perto do local onde de fato são utilizadas, nunca coloque dados sensíveis (como chave de api) dentro do código (sempre em um arquivo .env externo).

Crie um arquivo chamado tests.md dentro de .agents/rules e vincule em AGENTS.md. Escreva em português e dê exemplos, o propósito desse arquivo é conter as regras de testes, começando pelo seguinte: todo código deve ser coberto por testes automatizados (essa regra é crítica e não deve ser ignorada), o percentual de cobertura deve ser de no mínimo 80%, foque nos testes daquilo que é mais crítico (por exemplo, um checkout é mais crítico que um cadastro de categoria de produto), siga princípios como o test FIRST, que significa o seguinte, os testes devem ser FAST, ou seja, priorize testes que rodam rápido (usando test patterns como stub para evitar dependências externas lentas ou que tragam degradação de performance), os testes também devem ser INDEPENDENT, ou seja, não podem depender uns dos outros (caso contrário quando um teste quebra e ele é base para a execução de outro, o outro também quebrará), os testes devem ser REPEATABLE (ou seja, ao serem repetidos diversas vezes, os resultados devem ser os mesmos), por conta disso, lembre-se de usar test patterns como mock para evitar coisas como data, chamadas de api externa que voltam valores diferentes a cada chamada, os testes também deve ser Self Validated, ou seja, eles mesmos devem garantir que quebram frente a falhas de comportamento, ou seja, não é somente cobertura que conta, os retornos e o comportamento deve ser devidamente validado, tendo boas assertions/expects, a parte do Timely pode ser ignorada, crie os testes na ordem que fizer mais sentido para a eficiência da LLM, além disso, siga a estrutura Given/When/Then ou AAA (Arrange/Act/Assert) para ter testes bem estruturados, siga um conceito de pirâmide de testes, tendo uma base mais larga de testes de unidade, seguida de testes de integração e E2E. Para os testes utiliza a biblioteca vitest e para rodar os testes E2E prefira playwright. Foque em um conceito específico por teste (não misturando comportamentos diferentes, foque em requisitos), tanto o backend quanto o frontend devem ter testes abrangentes, para criar os testes E2E e ficar numa pasta fora do frontend e backend chamada de e2e.

Crie um arquivo chamado react.md em .agents/rules vincule no AGENTS.md, faça em português, com exemplos, tendo o seguinte: crie componentes pequenos e reusáveis (não crie componentes com mais de 30 linhas), evite passar props utilizando spread operator (<element ...props/>), evite useEffect desnecessário, utilize useMemo para evitar cálculos pesados entre re-renders, separe as responsabilidades de acesso ao backend do código do componente, utilize hooks com prefixo "use" para conter lógica que fica separada do código do componente, prefira componentes funcionais, sempre utilize propriedades de acessibilidade (aria-*), faça a estilização dos componentes utilizando tailwind.

Crie um arquivo folder-structure.md vincule em AGENTS.md, faça em português e coloque a estrutura de forma clara e objetiva. Remova de AGENTS.md a estrutura atual, siga os seguintes princípios: para o backend, utilize uma pasta chamada de routes (para lidar com o protocolo http), outra chamada de services (para as regras de negócio e comportamento da aplicação), outra chamada de data (para dados, queries, acesso a APIs externas), mantenha os tipos na pasta types (colocando um arquivo por tipo). No frontend, vamos ter uma pasta chamada de components (para os componentes), views (para as telas), services (para acesso ao backend), hooks (para os hooks), assets, types, além naturalmente das pastas de testes. Caso sinta necessidade de documentar mais alguma pasta pode inserir.
